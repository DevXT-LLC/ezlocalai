# GB10 LFM voice measurements — 2026-10-29

The physical GB10 can stream LFM speech, including MeanVC2 voices, faster than
playback when it is not competing with other inference. Concurrent inference
can cause audible gaps. Moving MiniCPM work onto the same LFM instance does not
by itself solve that contention.

## Uncontended calls

Direct and live-router paths each completed 33 responses without protocol
errors: five normal turns per voice, a 1200-word context update, cancellation
and recovery, paced microphone input, and a mocked tool call/result. The tools
never invoked WorkConductor. All six spoken questions and six tool exchanges
returned the expected information. No measured playback underruns occurred
with an 80 ms starting buffer. Cancellation acknowledgments were 48–69 ms
direct and 53–63 ms routed. Converted-call setup took about 3.7–3.8 seconds,
separate from the subsequent turn measurements.

Routed normal-turn medians, five observations per voice:

| Voice | First PCM packet | First energy packet | Generation RTF | Estimated untrimmed energy playout |
| --- | ---: | ---: | ---: | ---: |
| Native | 105 ms | 338 ms | 0.337 | 886 ms |
| British RP female | 171 ms | 510 ms | 0.350 | 1151 ms |
| Warm American narrator | 174 ms | 227 ms | 0.350 | 414 ms |

RTF is generation wall time divided by produced audio duration; less than one
means faster than playback. Packet arrival is not heard speech. Leading quiet
audio varied by voice. The final column estimates playout from 20 ms RMS windows
with a threshold of 98/32768 and an 80 ms initial buffer; breathing/noise can
cross that threshold. It is not a measured first intelligible word. No silence
trimming was added. Human listening, speaker similarity, cross-language quality
and long-call quality remain unvalidated. MeanVC2 has 16 kHz bandwidth despite
the 24 kHz wire format.

An isolated fully GPU-offloaded F16 control was slower: native/converted first
PCM medians 199/273 ms and RTF 0.451/0.474, versus Q4 107/165 ms and
0.321/0.341. Both streamed without measured underrun. Automatic batch settings
differed, so this is not a pure quantization experiment. Production Q4 was
preserved. Initial CPU-only diagnostic runs were excluded; the public harness
checks GPU offload to avoid mixing those results into GPU comparisons.

## Sharing the GPU and consolidating MiniCPM

Three normal converted turns per scenario; other scripted checks followed:

| Scenario | First PCM median | Generation RTF median | Largest lateness across the run, 80 ms buffer |
| --- | ---: | ---: | ---: |
| Two-slot LFM, no competing request | 171 ms | 0.341 | 0 ms |
| Production LFM plus continuous MiniCPM generation | 452 ms | 1.157 | 877 ms |
| Two-slot LFM plus continuous LFM generation | 896 ms | 1.332 | 2799 ms |
| Two-slot LFM plus intermittent LFM vision | 931 ms | 0.887 | 1151 ms |

The MiniCPM load completed 30 bounded requests. Shared LFM completed 13
background requests; the lighter vision load completed 16, correctly identifying
the synthetic red image in all 16. The vision trial used roughly 500 words,
a 384×384 image, a 64-token output cap and a one-second pause between requests.
It is a synthetic workload, not a replay of actual MiniCPM tasks. Average RTF
below one did not prevent burst-related playback gaps. The owned two-slot
container showed zero cgroup memory-limit/OOM events and zero CPU throttling.
Its idle control demonstrates that parallelism alone was not the slowdown.

The retained router history contained 86 MiniCPM requests among 500 records,
from 2026-10-28 21:55 UTC to 2026-10-29 01:50 UTC. Median prompt: 630 tokens;
maximum prompt: 5181; maximum prompt plus actual completion: 5208. These are
promising for LFM's supported 32768-token ceiling, but are MiniCPM token counts.
Retokenization, media expansion, requested output caps, accumulated call history
and task quality must be checked before migration. The isolated two-slot profile
split its configured 32000 total context into 16000 per slot.

Production remains unchanged at one LFM slot: a call reserves that slot for its
whole connection, so another request to that instance waits. A second slot
enables overlap but does not guarantee smooth speech. Before moving concurrent
helper work onto the voice instance, implement/validate voice priority or
admission control, or place competing inference on another worker. Removing an
idle resident MiniCPM model alone is not demonstrated to fix this issue.

## Reproduction and remaining work

Use `bench_lfm_realtime.py` with Python `websockets`; audio-input checks also
require ffmpeg. Keep connection credentials in an untracked private JSON file:

```json
{"base":"http://worker:8091","key":"YOUR_KEY"}
```

For routed checks add `worker`, `resource_base` pointing to the worker, and
`resource_key` if its authentication differs. Output redacts the two key fields.

```sh
python3 benchmarks/bench_lfm_realtime.py --connection /tmp/connection.private.json --output build/validation/voice --rounds 5 --context-words 1200 --audio /tmp/question.wav --tools
```

Compact evidence is in
`tests/fixtures/gb10_lfm_voice_20261029_validation.json`; local raw JSON, WAVs,
load drivers and logs remain under `build/validation/gb10-voice-20261029/`.
Owned benchmark containers, SSH forwards and duplicate benchmark model weights
were removed; production assets and rollback were retained. Existing MiniCPM
chat, embeddings, Whisper and Qwen TTS smoke checks passed. GB10 reverse tunnel,
image/music/video generation, multi-GPU and long-duration calls were not tested.

Next steps: profile concurrent batching/prefill and validate a voice-priority
policy; replay representative MiniCPM tasks with LFM and budget per-slot context;
human-listen to native/converted speech; verify a subsequent automated deployment
actually updates the running image. No WorkConductor code changes were made.
