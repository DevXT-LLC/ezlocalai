# Q4 KV tile loading on RTX 4090

In a controlled RTX 4090 comparison, decoding a retained 130K-token conversation
improves from **54.02 to 77.20 tokens/s (+42.9%)**. A 256-token response takes
**4.94 to 3.51 seconds (29.0% less)**. All 78 outputs, request fingerprints,
evaluated/reused counts and MTP counters match across six fresh engines.
Short decode remains approximately 112.8 tokens/s; cold bulk prefill is flat.

The eighth managed llama.cpp patch decodes packed Q4_0 KV tiles directly into
the existing F16 attention shared-memory layout. It avoids expanding the entire
active KV cache before each eligible MTP verification step. Model and KV bytes,
query precision, attention arithmetic and the original reduction partition are
preserved. The [contract](../patches/llama-cuda-q4-kv-fusion.md) describes the
metadata, layout and occupancy guards.

## Controlled full-engine comparison

Six fresh engines run production stock, candidate OFF, candidate ON, candidate
ON, candidate OFF, production stock. Only the candidate CUDA backend and exact
diagnostic flag differ. Requests run locally on the GPU host through the actual
engine with its production CUDA graphs enabled. The production executable,
other libraries, weights/projector, full arguments, inherited environment,
resource limits and read-only data mounts are retained.

Each engine handles 13 fixed requests: cold 4K/16K controls, three short
256-token decodes, finite seed/replay/append/rewind controls, and a public-source
130,005-token seed followed by three exact replays. There are no inference
retries or context reductions. Each deep return evaluates four tokens and
reuses 130,001, producing exactly 256 tokens with identical draft/accept counts.
All five production/OFF/ON repeat-pair checks pass; 11,220 tokens are generated
across the 78 measured outputs.

| Median measurement | OFF | ON | Change |
| --- | ---: | ---: | ---: |
| Deep cached decode, six samples per build | 54.017 tok/s | 77.204 tok/s | +42.9% |
| Deep complete response | 4,942.2 ms | 3,509.1 ms | −29.0% |
| Deep first output | 219.4 ms | 204.6 ms | −6.7% |
| Short decode, six samples per build | 112.777 tok/s | 112.877 tok/s | Flat |
| Cold 4K prefill, two samples per build | 2,535.5 tok/s | 2,538.7 tok/s | Flat |
| Cold 16K prefill, two samples per build | 2,983.8 tok/s | 2,983.2 tok/s | Flat |
| Cold 130K prefill, two samples per build | 2,096.8 tok/s | 2,096.7 tok/s | Flat |

Decode uses native `predicted_per_second`, which measures 255 intervals for a
256-token response. Timings are excluded from parity signatures. Both production
end controls remain approximately 54.0 tok/s for deep returns and 112.9 tok/s
for short decode. Each ON phase selects all 832 eligible host dispatches without
occupancy fallback; these include graph capture, rather than counting replays.
The last deep launch retains the same grid, block, shared memory, stream-K and
output partition at 130,304 padded KV rows and four query rows.

The low cached-return prefill rate divides only four newly evaluated tokens by
roughly 0.1 seconds of work. It measures a different workload from bulk prefill;
TTFT and reused/evaluated counts are the useful cache-return comparisons.
This patch targets three/four-query verification and does not accelerate a
1,024-token physical prefill batch. Network latency and GPU unlock causality
are outside this comparison.

## Automatic-default full-engine check

Three additional fresh engines run the final backend with OFF, unset AUTO and
explicit ON. Their 39 outputs match each other and all six previous phases:
**117 matching outputs and 16,830 generated tokens** in total. All 13 signature
fields and all 18 final-to-previous phase comparisons pass. Every deep return
still evaluates four tokens and reuses 130,001.

| Final mode | Deep decode | Complete response | First output |
| --- | ---: | ---: | ---: |
| OFF | 54.007 tok/s | 4,945.7 ms | 222.3 ms |
| AUTO | 77.229 tok/s | 3,509.8 ms | 205.0 ms |
| ON | 77.239 tok/s | 3,506.0 ms | 204.1 ms |

These are three returns in one phase per mode; the earlier ABBA remains the
primary performance estimate. The fresh AUTO process has the expected getter
export, no flag in its environment, zero exit-stat lines and a clean exit. All
three modes load the same final backend and unchanged remaining libraries.
There are no Docker, cgroup or host OOM events, and observed cgroup swap peaks
are zero. These tests qualify the final automatic path without a permanent
`.env` setting.

## Final build and numerical checks

The final backend enables the guarded path automatically with the environment
flag unset. Exact `0` disables it; exact `1` enables diagnostics. Other values
disable it. Default activation adds no diagnostic atomics or exit log. The final
hot SM89 stock/fused kernels have identical instruction and scheduling words to
the measured explicit-mode candidate. Stock/fused register counts remain 231/255,
with 16-byte stacks and zero local memory; actual device occupancy remains two
blocks per SM for both.

Final physical model-free checks pass:

- **25,427,968 half comparisons**, covering all 65,536 scale encodings, nibble
  values, packed layouts, alignment cases and long offsets. All non-NaN bits
  match; NaN classifications match and observed NaN payload differences are zero.
- **96 actual attention cases**, including near-context 230,000-active-token
  cases. Each of 2,113,536 float32 values matches across OFF, ON and unset AUTO.
  All input/guard bytes survive. For the 84 eligible cases, OFF overwrites the
  reserved F16 scratch witness while ON/AUTO preserve it; all 17 AUTO counters
  remain zero. The 12 excluded geometries retain their fallback behavior.
- Quick loader and AUTO attention memchecks report zero errors. Loader and
  selected fused AUTO racechecks report zero hazards, errors and warnings.

The initial unrestricted attention race gate failed on 12 warnings in the
unchanged two-query Q4 vector fallback. The deployed stock binary reproduces
exactly the same write/read PCs, hazard counts and multiplicities. The candidate
adds no observed warnings, and selected fused cases remain independently clean.
This is a narrowly scoped differential qualification: the inherited vector
warnings remain unresolved and are **not declared safe**. The original failed
gate remains in the evidence history.

All **394 CPU policy checks**, **eight focused engine checks** (18.32 seconds,
including 15 strict source fingerprints), and **73 oracle-free shipping checks**
(327.42 seconds) pass. Pristine installation, previous-prefix upgrades,
idempotence and complete eight-patch removal pass. All four platform recipes
carry the patch and CPU policy test. Both optional GPU oracle executables build
through the actual CMake `q4_kv_gpu_oracles` target; GPU execution is explicit
and remains outside CTest/package builds.
