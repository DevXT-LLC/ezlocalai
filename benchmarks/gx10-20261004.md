# GX10 / GB10 inference investigation

Measured October 4–5, 2026, on the GX10's 128 GB GB10. Application changes were
built locally, pushed to `fix/router-errors-24h`, and pulled on the GX10. No
production router deployment was performed. [HTTP timing samples](gx10-20261004.json)
exclude credentials and worker resource inventories.

## Embeddings

Qwen3-Embedding-0.6B Q8_0, 10,000-token context, batch/ubatch 512, full GPU
offload. Direct worker HTTP requests used unique inputs. The previous worker
logged 6.9 seconds for its first 50-token request; an independently observed
first short request took 3.046 seconds. Once warm, that same build was fast.
This was principally first-use initialization, not CPU inference.

The revised build warms actual text and a full microbatch before publishing each
resident CUDA instance. Its first short HTTP embedding took **15.5 ms**. Three
English/Spanish comparison vectors were identical before and after the change
(cosine similarity 1.0 for all three); dimensions and normalization also passed.

| Input | Old warm median | Revised median |
| --- | ---: | ---: |
| Approximately 40–50 tokens | 14.3 ms | 15.6 ms |
| Approximately 330 tokens | 28.5 ms | 29.9 ms |
| Approximately 3,030 tokens | 300.1 ms | 206.6 ms |
| Approximately 8,530 tokens | 702.7 ms | 690.4 ms |
| Four simultaneous ~330-token requests, per request | 80.9 ms | 82.8 ms |

These are three sequential samples per input size and one four-request burst,
not confidence intervals. The old 3K-token samples ranged from 206–304 ms, so
the median difference should not be treated as an established throughput gain.
Startup warmup moves the initialization cost; it does not eliminate that work.

The native sweep tested batch/ubatch 512, 1024 and 2048 against 4, 10 and 20 CPU
threads. Larger batches gave only small, inconsistent improvements (roughly 5%
at best on the long input). Keep the existing defaults and full context.

## Backend repairs and smoke measurements

The image now builds CUDA 13 native `sm_121` llama.cpp, TTS, image and music
backends. CUDA/cuDNN CTranslate2 is built from pinned source because the former
PyPI ARM64 wheel lacked CUDA. Torch and torchaudio are installed as a matched
2.9.1 CUDA 13 pair. Torch reports a 12.1 capability warning, but its CUDA tensor
operation and the tested speech/media operations succeeded; this is not a claim
that all PyTorch kernels are compiled specifically for `sm_121`.

| Workload | Previous failure | Revised result |
| --- | --- | --- |
| Whisper, 3.44-second audio | HTTP 500: CTranslate2 not compiled with CUDA | Correct transcript; 0.725 s first, 0.335–0.370 s warm |
| Native Qwen TTS | Missing torchaudio / unavailable CUDA setup | Valid WAV; roughly 4 s audio in 1.21–1.29 s |
| Image, 512×512 | HTTP 500: missing sd-cli | Valid image matching the cup prompt in 23.3 s |
| ACE music, 8 steps | No failure established | Valid 48 kHz WAV in 21.5 s; requested 10 s, actual audio 7.6 s |

Audio duration and media validity do not establish subjective quality across
voices, languages or prompts. The music duration discrepancy remains observable.

## Warm replica sizing and router queueing

Selected GB10 defaults: **two text slots, two embedding instances, two STT
instances and two TTS instances**. Image and video keep one generation each.
The tested GX10 used MiniCPM5-2B; other LLM model mixes need their own memory
budget. `MEDIA_KEEP_MODELS_LOADED=true` retains the pools during media work.

The [replica sweep](gx10-pools-20261005.json) tested 1/2/4 resident instances per
auxiliary service, each with client concurrency 1/2/4 and two four-request bursts
per setting. Text context, model quantizations and embedding context remained
unchanged. Random prefixes prevent embedding prefix reuse; TTS text changes
avoid cached audio. Four-client burst medians:

| Instances per service | Available RAM after startup | Four short embeddings | Four ~3K-token embeddings | Four transcriptions | TTS audio seconds / wall second |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 104.4 GiB | 0.113 s | 0.905 s | 1.504 s | 3.32 |
| 2 | 94.4 GiB | 0.096 s | 0.802 s | 1.482 s | 2.95 |
| 4 | 75.1 GiB | 0.096 s | 0.846 s | 1.542 s | 2.66 |

Two preserves overlapping requests without the extra ~19 GiB consumed by four.
More replicas do not add GPU compute or memory bandwidth. One instance had the
best TTS audio throughput, while two allows a second utterance to start before
the first finishes. TTS output lengths vary, so audio/wall throughput is more
useful than comparing burst wall times alone. These small samples support a
balanced default, not a universal optimum. Available RAM includes reclaimable
cache and varies with other host activity.

An earlier graph-enabled two-instance TTS run encountered a native CUDA illegal
memory access in the libmtmd audio decoder and silently recovered on CPU. Those
samples are excluded from the comparison. GB10 now disables CUDA graph replay
**only in TTS subprocesses** (`QWEN_TTS_DISABLE_CUDA_GRAPHS=true`). The revised
sweep completed **288 HTTP requests, including 72 uncached TTS generations**,
with every replica still on CUDA and no native error/CPU-fallback log entries.
This is a tested mitigation; it does not establish the exact upstream kernel
bug. `/v1/resources.model_pools` now reports every replica's actual device.

Router queues already default to no router deadline (`ROUTER_WAIT_TIMEOUT=0`).
The non-LLM dispatch path previously relied on heartbeats and could overfill a
worker between updates. It now atomically reserves each capability's slot until
the response/stream completes, queues dispatch races, and releases reservations
on failure/cancellation. Music-video reserves the shared music/video capacity.
Tests exercise queue/release behavior for embedding, TTS, STT, image, video,
music and music-video. Positive queue timeouts remain supported; external client
and reverse-proxy timeouts still apply. **These router changes await operator
deployment; production router code was not changed during this investigation.**

## Text generation

MiniCPM5-2B, the existing quantization/context/parallel configuration, greedy
sampling with seed 42, five prompts per fresh process, 128 generated tokens per
request. An off/on/off experiment with `GGML_CUDA_GRAPH_OPT` measured median
decode rates of **126.9 / 127.3 / 118.6 tokens/s**. All five output hashes matched
across the three processes, including reasoning text. The final control recovered
to 126.9 tokens/s by its last request. This is too small and noisy a difference
to justify changing the default; leave graph optimization at 0.

An earlier same-model 3090 comparison produced about 284 decode tokens/s. The
GX10's approximately 127 tokens/s is useful performance, but this build does not
make it match the 3090 for this workload. Short-request HTTP wall times should
not be compared when completion lengths differ.

## Video: Wan 2.2 replaces the legacy LTX default

The default now uses QuantStack Wan 2.2 A14B Q4_K_M high/low-noise experts,
Q8_0 UMT5 and the Wan 2.1 VAE through the pinned native `sd-cli` backend. T2V
and I2V select their own expert pairs. Downloads are pinned and cached. The
native child owns video allocations and exits before returning the encoded MP4.

Both initial Wan tests produced valid silent H.264 MP4s: 512×320, 33 frames,
24 fps (1.375 seconds), 18 total steps (8 high-noise, 10 low-noise), CFG 3.5.
Text-to-video took **338.9 seconds**; image-to-video took **347.8 seconds**.
The sampled first/middle/last frames showed a coherent blue cup, with the I2V
sample retaining the supplied cup image and a gradual camera move. One prompt
per mode does not establish general quality superiority. Text conditioning took
about 2.5 seconds and the T2V high-noise expert loaded in about 1.2 seconds;
denoising, rather than weight loading, now dominates this test.

These first tests still used the old unload/restore policy. Their post-video
embeddings took 18.2 and 15.6 ms, with all resident models back on CUDA. Health
requests stayed responsive during native generation, but pool restoration still
caused three-second probe timeouts. The GB10 profile now enables
`MEDIA_KEEP_MODELS_LOADED=true`: media requests retain other models, and the
router keeps advertising their free slots. Smaller GPU profiles retain the
existing handoff policy; explicit service unload settings override the GB10
default. Video requests remain serialized and native work keeps its lock through
cancellation. Concurrent GPU workloads can increase inference latency.

### Concurrent video with resident models

With four embedding, four STT and four TTS instances plus MiniCPM and the image
backend resident, another 18-step T2V completed in **347.4 seconds** while direct
requests exercised the other services. All 70 health probes returned HTTP 200;
no model unload/reload was recorded and every model remained on CUDA. The lowest
sampled available system RAM was **36.0 GiB**, including concurrent image generation.

| Request during video | Wall time |
| --- | ---: |
| Six short embeddings | 37.8–52.3 ms |
| MiniCPM, 28 generated tokens | 1.13 s (26.8 decode tokens/s) |
| Transcription, 3.44-second input | 1.77 s |
| Uncached TTS | 15.00 s |
| Image, 512×512 | 57.43 s |
| Short embedding after video | 15.4 ms |

This proves availability and memory headroom for the tested workload, not
unchanged latency under contention. Speech and text slow down substantially
while video occupies the GPU. A double increment in video request accounting
was also fixed so a resident video backend returns its router slot after each
success or failure; regression coverage includes repeated requests.

### Legacy LTX comparison

The first LTX-2.3 512×320/33-frame test took 854 seconds including downloads;
a cached follow-up took 606 seconds. Those tests used only eight denoising steps
(44.6 seconds in the first run), so the end-to-end comparison is not a matched
sampling-quality benchmark. LTX also reloaded three embedding instances on CPU
after video despite available system RAM; restarting restored CUDA. Wan's two
initial tests did not reproduce that recovery failure.

The legacy run showed long weight-copy pauses with one busy CPU core and low
GPU utilization. A one-time host cache-release diagnostic preceded progress,
but that uncontrolled observation does not establish a causal speedup. No
recurring cache flush or privileged-container requirement was added. See
NVIDIA's [shared-memory cache issue](https://docs.nvidia.com/dgx/dgx-spark/known-issues.html)
and the upstream [GB10 weight-copy investigation](https://github.com/vllm-project/vllm/issues/58726).

TTS caches audio across restarts. Repeated fixed-text probes can therefore measure
cache hits; the HTTP benchmark now randomizes its spoken test code. The TTS
generation timings in the table above are from the initial uncached probes.

## Reproduce

Use `scripts/benchmark_worker.py` for HTTP timings, then run the native scripts
inside the GB10 image with an otherwise idle GPU and the worker's environment
and model volumes. The scripts change only their own process settings.

```bash
python scripts/benchmark_worker.py --base-url http://GX10:8091 \
  --text-model openbmb/MiniCPM5-2B-GGUF --speech-file sample.wav --tts \
  --output gx10.json
python scripts/benchmark_embedding_native.py
python scripts/benchmark_llm_graph.py
python scripts/benchmark_pool_bursts.py --base-url http://GX10:8091 \
  --label replicas-2 --speech-file sample.wav --output pools-2.json
```

Josh's Docker group membership was corrected on the GX10 and verified with a
fresh login running `docker compose ps` without sudo. Existing shells need a
new login or `newgrp docker`.
